# 高中校友升学经验库：第一版功能与对象设计初稿

## 1. 项目定位

本项目面向高中在校生、毕业校友及相关维护者，目标是建设一个长期可维护的校友经验资料库，用于沉淀高考备考、志愿填报、大学专业体验、大学生活与后续发展等信息。

项目第一版不追求复杂社区化功能，而是优先完成一个清晰、可信、可检索、可投稿、可持续维护的静态信息平台。

核心目标不是“做一个网站”，而是把散落在不同校友个体中的经验转化为结构化、可复用、可持续积累的信息资产。

---

## 2. 设计原则

### 2.1 内容优先

第一版的核心价值来自内容质量，而不是功能复杂度。

网站应优先保证：

* 信息结构清楚；
* 内容来源明确；
* 文章可被快速检索；
* 经验具有参考边界；
* 投稿流程足够简单；
* 维护者可以低成本更新内容。

### 2.2 静态优先

第一版采用静态站思路，避免过早引入数据库、登录系统、评论系统和复杂后台。

静态优先的好处：

* 成本低；
* 部署简单；
* 安全风险小；
* 迁移成本低；
* 适合两人小团队维护；
* 适合内容型网站早期验证。

### 2.3 结构化优先

经验分享不应完全自由发挥，而应通过统一模板降低信息噪声。

同类内容应尽量保持相似结构，例如：

* 基本背景；
* 决策过程；
* 真实体验；
* 踩坑总结；
* 对学弟学妹的建议；
* 适用范围与局限。

### 2.4 可信边界明确

网站内容主要来自个人经验，不应包装成官方指导或确定性报考建议。

所有涉及志愿填报、学校选择、专业选择的信息，都应明确说明：

* 内容为个人经验；
* 仅供参考；
* 不构成唯一报考建议；
* 当年招生政策、专业组、选科要求、录取位次可能变化；
* 最终决策应以官方招生信息和现实条件为准。

## 3. 第一版产品目标

第一版目标可以概括为：

> 能看、能搜、能投稿、能维护、能说明边界。

具体目标：

* 访问者可以快速理解网站用途；
* 学生可以按主题、标签、关键词查找内容；
* 校友可以通过外部表单提交经验；
* 维护者可以通过 Markdown 或静态内容文件更新网站；
* 网站可以通过 Cloudflare Pages 等平台快速部署；
* 后续可平滑扩展到更复杂的内容系统。

## 4. 用户对象抽象

第一版至少考虑四类用户对象。

### 4.1 访问者 Visitor

访问者是所有进入网站的人，不要求登录。

典型访问者包括：

* 高一、高二、高三学生；
* 已毕业但仍关注升学信息的学生；
* 学生家长；
* 老师；
* 普通校友。

访问者主要行为：

* 浏览首页；
* 查看文章列表；
* 阅读文章；
* 使用搜索；
* 按分类或标签筛选；
* 查看项目说明；
* 进入投稿入口。

访问者不需要具备账号、权限或身份认证。

---

### 4.2 学生 Student

学生是网站的核心服务对象。

学生关注的问题包括：

* 如何准备高考；
* 某个分数段如何做志愿选择；
* 学校、专业、城市如何权衡；
* 某个专业到底学什么；
* 大学生活和高中想象有什么不同；
* 转专业、保研、考研、就业是否需要提前考虑；
* 学长学姐当年踩过哪些坑。

学生需要的不是碎片化故事，而是可比较、可检索、可理解的经验资料。

学生核心需求：

* 快速定位和自己处境相似的内容；
* 看到不同路径的真实案例；
* 理解经验的适用范围；
* 避免被单一叙事误导。

---

### 4.3 投稿者 Contributor

投稿者主要是往届毕业生。

投稿者可以贡献：

* 高考备考经验；
* 志愿填报复盘；
* 大学专业体验；
* 大学生活体验；
* 转专业经历；
* 保研、考研、就业经历；
* 对母校学弟学妹的建议。

投稿者核心需求：

* 投稿流程简单；
* 可以匿名；
* 可以选择公开哪些个人信息；
* 可以说明自己的经验适用范围；
* 可以保留必要隐私。

第一版不需要为投稿者提供账号系统。投稿可以通过外部表单完成。

---

### 4.4 维护者 Maintainer

维护者是网站的实际管理者，初期可以是项目发起人和朋友两人。

维护者职责：

* 设计网站结构；
* 维护代码仓库；
* 整理投稿内容；
* 审核文章；
* 统一文章格式；
* 更新标签；
* 发布新内容；
* 处理错误信息；
* 维护免责声明和隐私说明。

维护者核心需求：

* 内容更新流程简单；
* 不需要复杂后台；
* 可以通过 GitHub 协作；
* 可以预览和部署；
* 可以控制公开内容质量。

## 5. 核心内容对象抽象

网站不应只把所有内容都视为普通文章，而应抽象出几类稳定对象。

---

### 5.1 文章 Article

文章是网站最核心的内容对象。

一篇文章可以是：

* 高考经验；
* 志愿填报复盘；
* 专业体验；
* 大学生活记录；
* 转专业经验；
* 保研考研经验；
* 就业实习经验；
* 综合建议。

文章应包含以下基础字段：

```yaml
title: 标题
description: 摘要
date: 发布时间
updated: 更新时间
category: 主分类
tags: 标签列表
author: 作者信息
audience: 适合读者
visibility: 是否公开
reviewStatus: 审核状态
disclaimer: 是否显示免责声明
```

文章正文应尽量遵循对应模板，降低自由发挥带来的信息不稳定。

---

### 5.2 作者 Author

作者可以是真实署名，也可以是匿名校友。

作者对象不等于账号对象。第一版不需要登录系统，只需要在文章中记录展示信息。

作者字段建议：

```yaml
author:
  name: 匿名校友
  graduationYear: 2024
  highSchoolClass: 可选
  university: 可选
  major: 可选
  anonymous: true
  contactVisible: false
```

隐私原则：

* 不默认公开联系方式；
* 不强制公开真实姓名；
* 不公开未经授权的个人信息；
* 对学校、专业、届别等信息也应允许投稿者选择是否公开。

---

### 5.3 分类 Category

分类用于表示文章的主要内容方向。

第一版建议设置少量稳定分类：

```text

志愿填报
专业体验
大学生活
发展路径
项目公告
```

分类数量不宜过多。分类承担主导航作用，应保持稳定。

### 5.5 问题 Question

问题对象用于组织学生真正关心的场景。

网站首页和专题页不应只按文章时间排序，也应按问题组织内容。

问题示例：

```text
高三后期成绩波动怎么办？
学校优先还是专业优先？
去外省读大学值不值？
计算机专业到底适合什么样的人？
大学转专业难不难？
分数刚过一本线怎么报？
中外合作专业是否值得考虑？
医学专业真实压力有多大？
```

问题对象可以不独立建表，第一版可以作为静态页面或首页模块存在。

后期可以扩展为：

```yaml
question:
  title: 问题标题
  description: 问题说明
  relatedTags: 相关标签
  relatedArticles: 相关文章
```

---

### 5.6 投稿 Submission

投稿是尚未整理为正式文章的原始输入。

第一版投稿可以存放在外部表单系统中，例如飞书表单、腾讯问卷、金山表单等。

投稿字段建议：

```text
姓名 / 昵称
届别
是否匿名
当前大学
当前专业
分享类型
正文内容
是否允许公开学校和专业
是否愿意后续被联系
联系方式
备注
```

投稿处理流程：

```text
投稿者提交表单
↓
维护者查看原始投稿
↓
维护者进行格式整理
↓
必要时联系投稿者确认
↓
转换为文章
↓
提交到 GitHub
↓
审核后发布
```

第一版不建议做在线投稿后台。

页面是相对稳定的站点结构对象。

第一版基础页面：

```text

```

页面应服务于内容发现，而不是单纯展示视觉效果。

## 6. 第一版功能模块

---

### 6.1 首页模块

首页目标：

* 快速说明网站是什么；
* 提供主要入口；
* 暴露核心问题；
* 展示最新或精选内容；
* 引导校友投稿；
* 明确项目性质和免责声明。

首页建议模块：

```text
网站标题与一句话介绍
主要分类入口
问题导航
精选文章
最新文章
投稿引导
项目说明
免责声明提示
```

首页不应承载过多长文本。重点是让访问者快速进入具体内容。

---

### 6.2 文章浏览模块

文章浏览模块包括：

* 全部文章列表；
* 按分类浏览；
* 按标签浏览；
* 文章卡片展示；
* 文章排序。

文章卡片字段建议：

```text
标题
摘要
分类
标签
作者身份
届别
学校 / 专业
更新时间
是否匿名
```

第一版排序方式：

```text
默认按更新时间倒序
可手动设置精选文章
```

后期可扩展为：

```text
按热度排序
按推荐排序
按相关度排序
```

但第一版不需要。

---

### 6.3 文章详情模块

文章详情页是核心阅读场景。

建议包含：

```text
标题
摘要
作者信息卡
适合阅读人群
正文
标签
更新时间
相关文章
免责声明
```

作者信息卡可以展示：

```text
届别
大学
专业
内容类型
匿名状态
更新时间
```

文章底部建议展示：

```text
本文为个人经验，仅供参考，不构成唯一报考建议。
```

---

### 6.4 分类与标签模块

分类用于主路径，标签用于交叉检索。

分类页示例：

```text
/gaokao
/application
/majors
/university-life
/pathways
```

标签页示例：

```text
/tags/计算机
/tags/志愿填报
/tags/转专业
/tags/985
```

第一版要求：

* 每篇文章必须有一个主分类；
* 每篇文章可以有多个标签；
* 标签命名应统一；
* 不随意创造近义标签。

例如不要同时出现：

```text
计算机
计科
CS
Computer Science
```

应统一为一个标签，再在正文中自然表达其他说法。

---

### 6.5 搜索模块

搜索是内容型网站的核心功能之一。

第一版建议使用静态搜索方案，例如 Pagefind。

搜索对象：

* 文章标题；
* 摘要；
* 正文；
* 标签；
* 学校；
* 专业；
* 作者公开信息。

搜索页应支持：

```text
关键词搜索
搜索结果列表
结果摘要
跳转文章详情
```

第一版不强制做复杂筛选。后期可以扩展为：

```text
分类筛选
标签筛选
专业筛选
学校筛选
分数段筛选
```

---

### 6.6 投稿模块

第一版投稿模块不做后端系统，只做投稿说明页和外部表单入口。

投稿页内容：

```text
欢迎哪些人投稿
可以投稿什么内容
是否可以匿名
哪些信息会公开
哪些信息不会公开
审核流程
投稿表单入口
联系方式
```

投稿模块目标：

* 降低校友投稿门槛；
* 保护投稿者隐私；
* 让维护者获得结构化信息；
* 保持内容质量。

---

### 6.7 关于与说明模块

关于页应回答：

```text
这个项目是谁做的？
为什么做？
内容从哪里来？
如何审核？
如何投稿？
如何联系维护者？
项目和学校官方是什么关系？
```

如果不是学校官方项目，应明确说明：

```text
本站为校友自发维护的公益性信息整理项目，并非学校官方平台。
```

---

### 6.8 免责声明模块

免责声明可以作为独立页面，也可以合并在关于页和文章底部。

必须说明：

```text
本站内容来自校友个人经验，仅供参考。
本站不提供确定性志愿填报承诺。
高校招生政策、专业组设置、选科要求、录取位次每年可能变化。
请以教育考试院、高校招生网等官方信息为准。
涉及个人选择的问题，应结合家庭、兴趣、能力、政策和当年数据综合判断。
```

## 7. 第一版不做的功能

为了保持项目轻量，第一版明确不做以下功能：

```text
用户注册
登录系统
评论区
点赞收藏
私信系统
校友认证
在线后台
数据库
动态推荐
实时问答
AI 志愿填报建议
付费咨询
```

这些功能不是永远不做，而是不适合第一版。

原因：

* 增加开发复杂度；
* 增加审核压力；
* 引入隐私风险；
* 增加维护成本；
* 容易偏离内容沉淀目标。

## 9. 内容数据结构建议

以 Markdown 内容为例，每篇文章建议使用统一 frontmatter。

```yaml
---
title: "软件工程专业真实体验：适合什么样的人？"
description: "一位软件工程专业校友对课程、学习压力、就业方向和适合人群的复盘。"
date: "2026-06-10"
updated: "2026-06-10"

category: "专业体验"
tags:
  - "计算机"
  - "软件工程"
  - "专业选择"

author:
  name: "匿名校友"
  graduationYear: "2024"
  university: "华南理工大学"
  major: "软件工程"
  anonymous: true

audience:
  - "考虑报考计算机相关专业的高中生"
  - "想了解软件工程真实学习内容的学生"

review:
  status: "approved"
  reviewer: "maintainer"
  reviewedAt: "2026-06-10"

display:
  featured: false
  showDisclaimer: true
---
```

字段说明：

```text
title：文章标题
description：文章摘要，用于卡片和搜索结果
date：首次发布时间
updated：最后更新时间
category：主分类
tags：标签列表
author：公开展示的作者信息
audience：适合阅读的人群
review：审核信息
display：展示控制
```

## 11. 权限与流程设计

第一版不做复杂权限系统，但应在协作流程中区分角色。

### 11.1 内容来源状态

一篇内容可能经历以下状态：

```text
draft：草稿
submitted：已投稿
editing：整理中
reviewing：审核中
approved：已通过
published：已发布
archived：已归档
```

第一版可以不在系统中完整实现，但维护者内部应按这个流程处理。

### 11.2 内容发布流程

推荐流程：

```text
投稿者提交表单
↓
维护者初筛
↓
维护者整理格式
↓
必要时回访投稿者确认
↓
转换为 Markdown 文章
↓
创建 Git 分支
↓
提交 Pull Request
↓
另一名维护者审核
↓
合并到 main
↓
自动部署
```

## 12. 技术实现边界

第一版建议采用：

```text
静态站框架
Markdown 内容
GitHub 协作
Cloudflare Pages 部署
外部表单收集投稿
静态搜索
```

推荐技术组合：

```text
Astro
Markdown / MDX
Pagefind
GitHub
Cloudflare Pages
飞书表单 / 腾讯问卷
```

不依赖：

```text

服务器
登录系统
动态 API
自建后台
```

这样可以保证第一版足够轻、足够稳、足够容易迁移。

## 18. 总结

第一版网站应被定义为一个轻量、静态、结构化的校友升学经验资料库。

它的核心不是复杂功能，而是围绕以下三点建立长期价值：

```text
结构化：让经验可以被整理、比较和复用
可信度：让内容来源、适用范围和风险边界清楚
可检索：让学生能按问题、标签和关键词找到信息
```

第一版做到这些，就已经具备实际使用价值。后续是否发展为更复杂的平台，应取决于内容规模、访问量、投稿数量和维护能力，而不是一开始就追求完整社区形态。
